# Agent Behavior and Workflow Guidelines

## 1. Commenting Standards
- Avoid unnecessary comments. Do not write comments that simply describe a fix or explain obvious, easily understandable code.
- Keep all comments as concise as possible.
- Use comments **only** when necessary for the following purposes:
  - Logically dividing or structuring code sections.
  - Explaining highly complex or difficult-to-understand logic (always focus on the *why*, not the *what*).
  - Documenting methods, classes, and variables (e.g., standard docstrings).

## 2. Character Encoding Restrictions
- Strictly use ASCII characters for all code, scripts, comments, and general text.
- Avoid replacing standard characters with UTF-8 symbols (e.g., do not use em-dashes `—`, typographic quotes, or single-character ellipses `…`; use `-`, `"`, and `...` instead).
- **Exception:** You may use Language Symbols (like ä, ö, ü, and ß for German) when typing in that language.
- **Exception:** You may use UTF-8 characters inside string literals only if there is a deliberate technical reason for it (e.g., utilizing Nerd Font icons).

## 3. Git Workflow & Commits
- **Do not** automatically stage or commit changes unless explicitly instructed to do so by the user.
- When you have finished making modifications, provide a highly recommended commit message at the end of your response. Wait for the user to either execute the commit themselves or to explicitly ask you to do it.
- The commit message should summarize the work done since the last commit, not just the last change.

## 4. Context Window Optimization
- Whenever a commit has been successfully created (either by you or the user), you should trigger the `/compact` command to compress the conversation history and conserve the context window.
- **Exception:** If the commit was very small and the context is not that big (<10k tokens), this can be ignored.
- *Note: If your environment prevents you from executing slash commands autonomously, output a prominent reminder for the user to run `/compact`.*

## 5. Handling Missing Executables (Nix Environment)
- If a required program or CLI tool is not available in the current environment, do not fail immediately.
- First, check the project directory for a `flake.nix` or `shell.nix` file.
- If the required tool is provided in the project's development shell, execute your command within that shell (using `nix develop -c <command>` or `nix-shell --run "<command>"`).
- If the tool is not available within a project dev shell, utilize Nix to fetch it temporarily by prefixing your command with `nix-shell -p <package> [-p <other package> ...] --run "<command>"`.

## 6. Language Preferences
- Always answer user prompts in the language they were written in.
- By default, all code comments, commit messages, logs, and internal code documentation MUST strictly remain in English, regardless of the conversation language.
- **Exception:** Follow explicit user instructions overriding this default for specific artifacts (e.g., if the user explicitly requests "Write the Markdown files in German", fulfill that request).

## 7. Directory Navigation in Commands
- Do not prefix commands with `cd` into the current working directory.
- Use `cd` only when necessary, such as executing a chain of commands inside a different target directory. Prefer passing direct file paths where possible.
